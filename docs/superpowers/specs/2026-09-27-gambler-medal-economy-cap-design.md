## 2. 已核对的源码与改动边界

- `internal/platform/unified_assets.go` 已汇总 Native Active、Reserve、Available Chips、德州本人桌上筹码/投入及可确认的在途资金，并避免 Reserve→Active 重复计数；它不是所有游戏资金已经覆盖的证明。

- `internal/roulette/settlement.go` 维护托管与实际入账的守恒；`history.go` 对照逐笔账本验证，不能只改显示金额。
- `internal/poker/hand.go` 在每手结束时把赢款记入桌上筹码，而不是到离桌才结算。封顶必须在这里生效，不能只限制提现。
- `internal/rankings/read.go` 在数字快照上实时关联公开档案；`web/src/rankings/Rankings.tsx` 有可复用的姓名单元格。现有前三名的名次装饰不等于个人勋章。

复用现有账本、操作幂等、后台预览/确认/审计、资产汇总和 CDN。只增加本次政策及一枚纪念勋章所需的数据，不建设通用成就引擎、勋章商店或新上传系统。

## 3. 金额、总资产与结算口径

### 3.1 精确金额

沿用 1 API Credit / 1 Chip = 500,000 raw units。服务端使用经过溢出检查的整数；JSON 金额使用十进制字符串，前端用 BigInt，不经过 Number。

| 数值 | raw units |
| --- | --- |
| 十亿资格线 | `500000000000000` |
| 一百万每局投入 | `500000000000` |
| 一千亿资产上限 | `50000000000000000` |
| 一万 Reserve | `5000000000` |

资产上限的 raw 数值超过 JavaScript 安全整数范围。沿用现有 Native 单次划转的独立增量上限，本次不放大该接口上限。

### 3.2 统一所有权

总资产包含 Native Active、Reserve、可用筹码、本人桌上筹码、本人仍在风险中的本金以及可确认归属的在途资金。每笔资金只算一次。

- 未结束的单人局和轮盘局按本人尚未释放的投入本金计，不按整局奖池或潜在中奖金额计。
- 德州按本人桌上余额与尚未结算的本人投入计，不把他人投入算作本人资产。
- 本金退回、取消退款、德州未跟注部分退回、离桌回款、钱包内部兑换与划转是资产位置变化，不是新奖金，不重复扣减。
- 已亏损、已确认销毁的资金退出总额；额度消费正常减少 Native Active。
- 资产来源不完整、在途状态不明时，不用零值替代，也不把小时榜当实时余额。新局在揭晓前检查依赖；已受理局保留原结果，由后台按原操作编号恢复，不让用户手动决定账务事实。

Native Active 保持不变优先于追溯削减旧资产。若上线前仅 Native Active 就已超出上限，保留并在操作预览中单列；这类账户仍可正常损失或消费，但没有新增游戏收益空间。不得为凑齐一千亿偷偷清除原生额度。

Native 是独立系统：其余额读取需带观测时间，平台划转使用既有账户锁与原始回执。平台可控制的正向增加均须纳入封顶检查；若有绕过平台的 Native 人工充值，先报告并对齐该写入入口，不把“读取一次 Native 余额”宣称为跨系统原子封顶。上述存量或外部写入例外必须显式记载，不能伪称所有历史账户已降至上限。

### 3.3 B 方案的计算

在同一笔结算中，`T` 是包含本局未释放本金的当前总资产，`S` 是该用户本局累计实际投入，`P` 是原游戏规则产生的含返本派彩，`C` 是总资产上限。德州未跟注退回额先作为中性归还处理，不算中奖，计算时从 `S` 中剔除；`T` 仍包含这笔已归还的自有资金。

```text
returned_principal = min(S, P)
gross_profit = max(P - S, 0)
base = T - S + returned_principal
credited_profit = min(gross_profit, max(C - base, 0))
credited_payout = returned_principal + credited_profit
cap_withheld = P - credited_payout
total_after = base + credited_profit
actual_net = credited_payout - S
```

`credited_profit` 向下对齐该游戏既有的最小可入账单位，剩余差额也计入 `cap_withheld`；不得制造德州引擎不接受的零碎筹码。不为封顶改动结果概率、中奖倍率或 RNG。

以 Credits 为单位的例子：

| 结算前 T（含本金） | 本金 S | 原规则派彩 P | 实际派彩 | 封顶未入账 | 结算后总资产 |
| --- | --- | --- | --- | --- | --- |
| 99,999,999,900 | 100 | 500 | 200 | 300 | 100,000,000,000 |
| 100,000,000,000 | 100 | 500 | 100 | 400 | 100,000,000,000 |
| 100,000,000,000 | 100 | 0 | 0 | 0 | 99,999,999,900 |
| 100,000,000,000 | 100 | 100（返本） | 100 | 0 | 100,000,000,000 |

达到上限仍可正常下注；输掉后腾出的空间可供之后的实际盈利使用。并发结算按数据库实际提交的串行次序消费剩余空间，重复请求返回第一次的原回执，不重新分配空间。

## 4. 账务、版本与公共展示

### 4.1 事务与幂等

所有受影响账户采用一致的锁顺序。房间/局锁之后，按用户 ID 升序取得共用账户级锁，再按固定顺序锁相关钱包；只做账户操作的路径不反向等待房间锁。资产计算、封顶决定、实际入账、封顶差额和结算终态一起提交。

不能把封顶塞进通用 `ApplyInTx` 后静默改变调用者请求的金额；调用者、账本、玩法历史和供应量统计必须明确使用同一份结算结果。封顶不是异常，不落入 `NEEDS_REVIEW`。真实来源冲突或外部依赖故障沿用后台恢复机制。

- 单人游戏保留原始派彩证据，实际发行/销毁按实际净变动统计。
- 轮盘结算记录实际发放和封顶销毁，守恒关系变为：投入 = 退款 + 实际派彩 + 封顶销毁 + 剩余托管。销毁不转给管理员或其他玩家。
- 德州在每手结束时先保留完整引擎结果与底池原始分配，再对赢家新增收益应用封顶调整并更新实际桌上筹码；回放分别验证底池结果与该调整。下一手只能使用调整后的真实筹码。不能只改 session 余额而让状态、事件或历史验证互相矛盾。
- 实际入账为零时仍有不可变终态回执，遵守现有零 delta 不写账本腿的契约。
- 既有签到、按时领取等奖励也遵循剩余容量并记录实际发放；管理员正向调账超过容量时拒绝整笔并展示原因，避免静默改写管理员指定值。退款和已有本金迁移不作奖励裁剪。

### 4.2 政策与历史

新增不可变的经济政策版本，保存单人累计投入上限、总资产上限、B 方案及其 hash。新局/新手在开始前绑定政策，旧局使用原绑定，历史回放不能读取“当前政策”重算过去的入账。

现有投注策略同时被单人游戏和轮盘使用，不能直接把共享策略全改成一百万。单人上限只由单人入口和二十一点每次追加校验；多人保持自身策略。上线切换前让旧局收尾，避免跨政策的资金悬挂。

回执增加独立的原规则派彩、实际派彩、封顶未入账、实际净变化和经济政策版本字段。原字段的历史语义保留，旧回执等价于无封顶。开奖、公平性、派奖三个事实分别展示：公平性通过不意味着没有封顶差额。

排行榜资产值和盈利值使用实际资产/实际净收益；“最大单局回报”保留原指标定义，只将其中的入账金额改为封顶后的实际金额，不偷偷改成另一种净利指标。总投注额继续使用实际投入。历史已发布快照保留；新政策从生效点影响新的累计统计。

规则继续放在既有折叠区域中，但首次执行受新政策约束的下注前须能清楚看到上限说明；发生裁剪的结果区直接展示“原规则派彩 / 实际到账 / 封顶未入账”，不能只藏在公平性详情里。

## 6. 一次性发放与后续重置流程

1. **资格快照与授予**：先公布快照安排，短时阻止新的资产迁移、下注和 API 消费准入，允许已受理操作按原规则收尾。待账务可确认时记录实际快照截止点，不倒填为本次对话时间。核实全部资产分项后锁定资格清单，预览人数和影响，确认后幂等发放并恢复正常准入。该动作不重置资产。
2. **重置预览**：在用户决定执行重置时，再进入维护窗口。暂停新局、资金迁移、自动补足、新奖励任务和 API 新请求准入；排空旧局、桌上资金、在途划转、已受理 API 消费及旧注册奖励任务。禁止用户在冻结间隙把待重置 Reserve 换到保留的 Native Active。
3. **固定目标与检查点**：确定纳入重置的现有账户集合，包含管理员和零余额账户；操作期间不让新注册混进半套快照。创建私有备份、余额与账本检查点、Native 余额快照和差额预览，显示受影响账户数及增加/减少的总量。
4. **明确执行后再记账**：每个账户在事务中通过现有不可变账本追加 Reserve 调整至 10,000、Available Chips 调整至 0 的差额；已经等于目标的账户记录无余额变动的完成回执。活动 ID + 账户作为稳定幂等键。禁止直接 UPDATE 余额或删除旧交易。
5. **恢复与验收**：允许批次中断后按同一 ID 续跑，已完成账户不再次重置。全部完成、Native 前后相等、旧在途为零且账本一致后，启用新政策、恢复服务并发布一次新的资产榜快照；随后仍按每小时节奏更新。旧游戏历史和勋章均保留。

如果有真正未能确认的旧账务，保留维护状态并报告具体未决项，不带着“旧资金之后可能回流”的状态启动重置。运营重置差额单独分类，不算游戏盈利、下注、救济收入或本次勋章资格。

本次不重置排行榜的历史盈利、投注记录或 API 用量；用户未要求清除这些统计。未来新注册仍按既有注册奖励规则，不被本次一次性重置自动改为一万。
